**Bug found on the first live run, fixed, recorded in `ai/memory.md`:** the tier-expansion job rescheduled its own successor from inside its own BullMQ processor, reusing the same job id. The instant the tier-N job's handler returned, `removeOnComplete` deleted the Redis key it was stored under — which by then held the just-added tier-N+1 job, since both shared one id. Tier 1 fired correctly and tier 2 silently vanished, with no error anywhere. Fixed by giving each (task, tier) pair its own job id and sweeping the whole plausible tier range on cleanup instead of tracking "the" pending id. Re-verified live: the tier-2 job now persists in `delayed` state with the correct compressed delay.

**Deliberate design note:** the worker feed (`findNearbyTasks`, Phase 4) is unaffected by tier/offer state — any eligible nearby worker can find and accept a published task by browsing regardless of whether a formal offer exists yet. This means a total matching-pipeline failure (Redis down) degrades to "found by browsing, not by notification," never to "invisible." There is deliberately no push/email notification sent on an offer yet — that channel doesn't exist until Phase 8 — so `TaskOffer.notifiedAt` is left null rather than falsely marked as sent.

**The one bug this phase's own verification practice was built to catch, found live:** `ReviewService.completeApproval` originally read `task.status`, decided a dispute was not open, and only THEN wrote `COMPLETED` — a plain `update`, not a conditional one. A dispute raised in the gap between the read and the write would have been silently overwritten, exactly the race docs/14-dispute-resolution.md calls out by name ("a dispute raised one second before the 24-hour auto-approval deadline must win that race"). Fixed by making the status write itself the race guard: an atomic `updateMany` scoped to `status IN (SUBMITTED, UNDER_REVIEW)` that only releases payment if it actually flips zero-to-one row, with a symmetric fix applied to `reject()` and to `DisputesService.raise()`'s own freeze. This is also what makes two concurrent `autoApprove` calls on the same task safe without coordinating — a property the codebase already relied on, now explicitly extended to cover disputes too. 7 fake-Prisma unit tests lock this in; the live concurrent-request test (`Promise.all` firing both endpoints at once) is what actually proved it under real HTTP, real auth, and a real database.

**Admin console UI**: none of this has a screen yet. Every admin action above is a real, working, audited API endpoint — the web app phase is what gives an admin a page to click through instead of a `curl` command.
